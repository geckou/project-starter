### Q-007 Firestore のデータとルールを、名前付きデータベースで環境ごとに分けるか

- 発生: 2026-11-25 / #408（相乗り構成を唯一の構成にし、Functions を環境別に配る）の対応中
- 種別: データモデル / セキュリティ
- 状況: Functions は環境ごとに配り分けられるようにした（`develop-api` / `staging-api` / `api`）。
  Firestore は (default) DB 1 つを全環境で共有しており、develop / staging から本番データに触れるうえ、
  ルールを staging で先に確かめる場所が無い。#408 の提案 3 で「要検討」とされた部分
- 選択肢:
  - A) 環境ごとに名前付き DB（`develop` / `staging` / (default) を本番）を持つ（推奨）— データが環境で分かれ、
    `firebase.json` の `firestore` を配列にすれば DB ごとにルールを持てる。ただし `--only firestore:<DB>`
    相当で staging の DB だけへ配れるかは**未検証**。Admin SDK / クライアントの DB 指定、エミュレーター、
    ルールテストの分岐も要る
  - B) (default) DB を共有したまま、コレクション名の接頭辞（`stg_` / `dev_`）で分ける — 今の
    `firestore.rules` のコメントの方式。追加の仕組みは要らないが、ルールは全環境で 1 つのまま
  - C) 現状維持（全環境で同じデータ・同じルール）
- ブロック: Firestore の環境分離（ルール・Admin SDK・クライアントの DB 指定・`deploy-targets.mjs` の `firestore` の扱い）
- 進めた範囲: #408 で Functions の配り分けまで。Firestore は production からだけ配る従来の扱いのまま

### Q-008 課金のシークレットを環境ごとに分けるか

- 発生: 2026-11-25 / #408 の対応中
- 種別: セキュリティ / 外部サービス連携
- 状況: `staging-api` は `api` と同じコード・同じ `defineSecret`（`STRIPE_SECRET_KEY` など）を使うため、
  Secret Manager の**本番の値**がマウントされる。staging の QA で Checkout を通すと本番キーで課金が走りうる。
  #408 以前も staging のクライアントは本番の `api` を叩いていたので悪化ではないが、staging で関数を
  検証できるようになった以上、キーも分けないと検証にならない
- 選択肢:
  - A) 環境ごとに別名のシークレットを持つ（`STRIPE_SECRET_KEY_STAGING` など）（推奨）— `api.ts` を
    環境ごとに関数を作るファクトリにし、環境に応じたシークレットを宣言する。`index.ts` のグループは
    同じオブジェクトの使い回しではなくなる
  - B) シークレット名は共通のまま、staging では `.env.staging` に置いたテストキーを優先して読む — 別名の env を
    読む分岐が要る。テストキーが関数の環境変数（閲覧者ロールから読める）に載る
  - C) 現状維持（staging でも本番キー。staging では課金を試さない運用で避ける）
- ブロック: staging での課金フローの検証
- 進めた範囲: なし（課金・外部サービス連携のため保留）

### Q-005 「管理下にあるリポジトリへの PR」は自律性の境界の 3 段目か

- 回答: 2026-09-07 / **A（3 段目を「管理下にない」リポジトリに限定する）を採用**
- 判断の理由:
  - PR は出した時点では取り消せる（マージは人が決める）。3 段目の基準である
    「取り消せない・外に出る操作」に当たらない
  - 元の指摘（「いちいち許可取らなくていいんだけど」）への対応がこれで完結する
  - 「管理下」の線引きは geckou の Organization にあるかどうか
- 反映済み: CLAUDE.md「自律性の境界」3 段目を
  「**管理下にない**リポジトリへの Issue・PR の投稿」に変更し、管理下のリポジトリへの
  PR 作成は 3 段目でないことを明記。親テンプレートへの Issue は公開前提のため
  従来どおり内容を確認してから立てる（`.claude/docs/upstream-report.md`）
- 再考の目安: 管理下のリポジトリに、出しただけで外へ影響する PR
  （公開パッケージの自動リリース等）が増えたら線引きを引き直す

### Q-006 `.github/` 配下を層マニフェストに登録するか

- 回答: 2026-09-07 / **A（層に属さないものとして明示する）を採用**
- 判断の理由:
  - `.github/` の中身（CI・デプロイ・ブランチ保護・PR / Issue テンプレート・テンプレート同期）は、
    どの層を選んだ派生プロジェクトでも同じように要る。層構成で要否が変わらない
  - `files` は「その層と一緒に消えるもの」の一覧であって、リポジトリのファイル一覧ではない。
    消えないものを載せると、一覧の意味が「登録漏れを探す対象」に変わってしまう
  - B（core へ登録）は core が `removable: false` なので動作が変わらず、
    表示上の意味だけが増える
- 反映済み: `.claude/docs/layers.md`「マニフェストの書き方」に
  「何を登録し、何を登録しないか」を追記（判断基準は
  **その層を外したときに消えるべきか**）。`layers.json` は変更なし
- 再考の目安: 層によって `.github/` のファイルごと要否が変わるものが出てきたら、
  そのファイルだけ該当層の `files` へ入れる

### Q-001 使わないプロバイダのシークレットもダミーで作らせるか、宣言側を可変にするか

- 回答: 2026-09-06 / **A（このまま。使わない側はダミー値で作る）を採用**
- 判断の理由:
  - B（`BILLING_PROVIDERS` を足す）は既定を「両方」にする限り、結局 3 つ作らないと
    デプロイが落ちる。既定を変えれば今度は課金が黙って 503 になる。
    「知らないと踏む」点が変わらないのに、設定のノブだけ増える
  - C（プロバイダごとに関数を分ける）はエンドポイントの URL 構成とデプロイ単位が変わる。
    直す対象（秘密の置き場）に対して影響範囲が大きすぎる
  - A は追加の設定がゼロで、踏んだときのエラーが firebase-tools 側から
    「どの秘密が無いか」を名指しで出る。手順を 1 行増やすだけで足りる
- 反映済み:
  - `.claude/docs/billing.md` 1-2 節に手順（`printf '' | firebase functions:secrets:set X --data-file -`）
  - 同ファイルの完了チェックリストに「使わないプロバイダの分もダミー値で作った」
  - `apps/functions/src/lib/billing.ts` の `BILLING_SECRETS` にも同じ注意
- 再考の目安: 「片方だけ使う」構成が実際に増えて、ダミー作成の漏れが繰り返し起きるようなら B を入れる
